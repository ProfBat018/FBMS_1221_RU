# Load Balancer

Здесь начинается введение в микросервисную архитектуру.

Начнем с того, что такое Load Balancer.

`Load Balancer` - это устройство, которое распределяет входящий сетевой трафик между несколькими серверами.

Но в программировании, `Load Balancer` - это программное обеспечение, которое выполняет ту же функцию, что и оборудование.

По факту мы принимает запрос и перенаправляем его на один из серверов, который обрабатывает запрос. Это даже может быть один и тот же сервер, но разный порт.

Давайте разберем пример монолитной и микросервисной архитектуры.

## Монолитная архитектура

В монолитной архитектуре у нас есть одно приложение, которое выполняет все функции.

Тут важно понимать, если вы просто взяли и отделили `Backend` от `Frontend`, это не микросервисная архитектура. Или же если вы используете несколько `Web Api` в одном приложении, это тоже не микросервисная архитектура. То что у вас в `.sln` файле несколько проектов, это не микросервисная архитектура. Здесь я попытался объяснить все нюансы, которые мешали мне во врем обучения микросервисной архитектуре.

До сих пор мы писали на монолитной архитектуре, но теперь мы переходим на микросервисную. Опять таки тут важно понимать нужно ли нам это вообще ? Если посмотреть на количество успешных стартапов, то большинство из них начинали с монолитной архитектуры. Потому что это быстрее и проще. Но когда вырастаешь, то начинаешь сталкиваться с проблемами монолитной архитектуры.

Соотвестенно я вам советую не идти сразу на микросервисную архитектуру, а начать с монолитной. Потому что микросервисная архитектура требует больше времени, ресурсов и опыта.

Даже не во всех больших проектах используется микросервисная архитектура. Например, `Facebook` и `Google` используют монолитную архитектуру.

В последние года есть большой хайп на микросервисную архитектуру, но это не значит, что она подходит всем. Начал этот хайп компания `Netflix`, которая перешла на микросервисную архитектуру и это им помогло.

## Микросервисная архитектура

В микросервисной архитектуре у нас есть несколько микросервисов, которые выполняют разные функции.

Чтобы реализовать такую архитектуру есть несколько условий, которые нужно выполнить:

1. Каждый микросервис должен быть независимым.
2. Каждый микросервис должен быть масштабируемым.
3. Каждый микросервис должен быть отказоустойчивым.
4. Каждый микросервис должен быть легко заменяемым.

Можно задать ризонный вопрос - как реализовать микросервисную архитектуру с точки зрения программирования ?

Для этого есть несколько паттернов, которые помогают реализовать микросервисную архитектуру:

1. `API Gateway` - это паттерн, который позволяет объединить несколько микросервисов в один API.
2. `Service Discovery` - это паттерн, который позволяет микросервисам находить друг друга.
3. `Circuit Breaker` - это паттерн, который позволяет избежать ошибок в микросервисах.
4. `Load Balancer` - это паттерн, который позволяет распределять нагрузку между микросервисами.

Формать `deployment` должен быть в формате оркестратора контейнеров, например `Kubernetes`.
Каждый ваш микросервис должен быть в контейнере, например `Docker`.
Это нужно для того, чтобы вы могли легко масштабировать и управлять вашими микросервисами.
Так же это является неотъемлимой частью `отказоустойчивости`. Так как если один из ваших микросервисов упадет, он сразу перезапустится.

И так начнем с `Load Balancer`.

## Load Balancer

По сути `Load Balancer` - это сервис, который перенаправляет запросы на один из серверов, который обрабатывает запрос. Он работает по максимально простой схеме - он принимает запрос и перенаправляет его на один из серверов. Вот пример `yaml` файла, который описывает `Load Balancer`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: redis-sql-service
spec:
  selector:
    app: redis-example
  ports:
    - name: redis
      protocol: TCP
      port: 6379
      targetPort: 6379
    - name: web-api
      protocol: TCP
      port: 8080
      targetPort: 8080
    - name: ms-sql
      protocol: TCP
      port: 1433
      targetPort: 1433
  type: LoadBalancer
```

Есть еще более сложные схемы, с использованием `bash` скриптов, но это уже зависит от вашего `deployment` файла.

Вот пример `bash` скрипта, который описывает `Load Balancer`:

```bash
kubectl expose deployment redis-sql-deployment --type=LoadBalancer --port=6379 --target-port=6379 --name=redis-sql-service

kubectl expose deployment redis-sql-deployment --type=LoadBalancer --port=8080 --target-port=8080 --name=redis-sql-service

kubectl expose deployment redis-sql-deployment --type=LoadBalancer --port=1433 --target-port=1433 --name=redis-sql-service
```

Его можно использовать как для распределния нагрузки между серверами, так и для обеспечения отказоустойчивости. Так и для правильного переноса трафика между серверами.
